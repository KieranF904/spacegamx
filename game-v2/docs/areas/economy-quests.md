# Economy, items and quests
Everything a pilot owns and earns: the item catalogue and recipes, cargo/storage stacks, credits and XP, the refinery/fabricator/market, trade between pilots, loot pods and salvage, jobs (quests, bounties, operations), reputation and skills, ribbons, outposts (the pilot's own station), and the saved `PlayerProfile` with its migrations. Rules live in `common/src/econ` (pure, shared with the client); the server side (`server/src/game/*`) enforces them; the client has windows only.

## Public interface
- Catalogue: `ItemCatalog.get(id)`, `Economy.items/recipes`, `RecipeBook.partInputs(part)`, `partItemId`/`parsePartItemId`. Prices: `sellPrice`, `buyPrice`, `saleTotal`, `vendorPrice`.
- Stacks: `Stack {id,n}`, `Bag = Record<string,number>`; always use the stacks helpers.
- Pilots (server): `pilots.give(conn, bag, {toStorage?, source?, at?, quiet?})` (returns what did not fit), `take(conn, bag, 'cargo'|'storage'|'any')`, `addCredits`, `addXp`, `bumpStat`, `grant({plans,recipes,licences,reputation,skillPoints})`, `get(conn)` (the profile), `connOf(eid)`, `onEvent`, `markDirty`, `toast`.
- Quests (server): `quests.onKill(conn, enemy, faction, system)`, `acceptFrom`, `opCount/opAdvance/fail`, `canEnter(conn, systemId)` (sector licences).
- Pods: `pods.spawn/scatter/take/near`; Towing: `towDelivered(pilot, target, kind)` in game/Derelicts.ts (GameServer calls it); Support: `support.note(healer, target, hp, now)`, `supporters(target, now)`.
- Kill pay: `Enemies.onDestroyed` (game/Enemies.ts ~l.1255): `faction.ships[type].xp/credits` x `gradeReward` (xp) and x `rules.gradeCredits[grade-1]` (credits), elite x `rules.eliteLoot`, party members 0.75 xp / 0.4 credits within `PARTY_SHARE_RANGE`, supporters (Support ledger) paid like party but without job credit. Bosses: Bosses.onDestroyed.
- Profile persistence: `PlayerProfile`, `migrateProfile(raw, kit, catalog, { econ })` (without `catalog` a pre-v4 save waits, without `econ` a pre-v5 one); stores in server-core.md.

## Invariants
- The server is the only authority: every economy message is a request, checked (docked/in range? licence? goods held? room?) and answered with new state. The client never changes inventory.
- Items conserve: moves go through `give/take`; never `profile.cargo.push` directly; use `hasAll`/`removeAll` before changing anything (all-or-nothing).
- Cargo capacity is volume; mass (ships/load.ts) affects flight: `cargoMass` is replicated in the pilot row.
- Everything craftable opens at its level; schematics are retired (`retired.ts`). Do not reintroduce items that teach.
- A bounty/fleet job id rebuilds the job (`bountyDef(id)`), so ids are deterministic from station + time window.
- Credits and XP changes go through `addCredits/addXp` (loan repayment share `LOAN_REPAY_SHARE` 0.25, level-up handling, ribbons).
- `migrateProfile` never throws on junk and never loses data it can keep; bump `PROFILE_VERSION` only for structural migrations; a save that fails to load/migrate is never overwritten.
- Item and recipe ids in quests, drops, vendors, people and codex must exist: `checkGameData` (server/src/data/validateGameData.ts) enforces it at server start and in tests.
- Lore (docs/lore-canon.md): every lore claim in quest text, dialogue and codex needs an owner in the game (a named person who might be wrong); narration never states contested lore as fact; the cluster never speaks; no hint hides anything the player needs. Audit new text against the 7 rules at the top of lore-canon.md, not just against prose style.

## How to extend
1. **Add an item**: append an object to `data/items.json` (`id, name, category, rarity, value, color, description` plus optional `volume/mass/family/tier/short/ammoFor/socket/codex`). If it is made: add a `craft` recipe in recipes.json (`id, out, inputs, time, level?`). Ship parts and plans are generated; for a new part model go through ship-parts (scripts/econ/models.mjs generates models/recipes/items entries; do not hand-edit generated lines). Run the item/validate tests.
2. **Add a recipe**: `refining` (`inputs, out, time, level?`) or `craft` in recipes.json; `starter:true` or `level`/`quest` gate; server enforcement is in `StationServices` (`refine`, `craft`) via `canCraft`.
3. **Add a quest**: append to `data/quests.json` `quests[]` with `steps` (kinds in `QuestStepKind`, quests.ts ~l.29-100), `rewards`, `requires`, `person`/`giver`. For a new step kind: add to the union, `stepText`, `stepCount`, handle in `Quests.ts` (`onKill`/`tick`/`opSteps`) and `validateGameData`. People lines go in `data/people.json` (dialogue shapes in econ/dialogue.ts; talk handled by `People.handle`).
4. **Add a reputation or vendor**: `reputations` in quests.json (+ `vendor.stock` with `rank`); prices via `vendorPrice` and `RANK_DISCOUNT`.
5. **Add a ribbon**: entry in data/achievements.json (`stat` must be in `KNOWN_STATS`, validateGameData.ts ~l.147; bump the stat with `pilots.bumpStat`).
6. **Add a profile field**: add to `PlayerProfile`, default in `newProfile`, tolerant copy in `migrateProfile` (a `cleanX` helper), set `markDirty` where it changes, send it in `sendProfile` and `ServerProfileMessage` if the client shows it (econProtocol.ts). Bump `PROFILE_VERSION` only if old saves need real conversion. Add a case in `econ.test.ts` or `players.test.ts`.
7. **Add an economy message**: econProtocol.ts (client + server interfaces), a forwarding entry in `registerModuleHandlers` (net/handlers/modules.ts) calling the module (e.g. `ctx.services.sell`), client send in the window; see networking.md.
8. **Add a pay source**: credits via `pilots.addCredits`; XP via `addXp`; party share via `PilotHost`; support share via `Support.supporters` (see Enemies.onDestroyed).

## Gotchas
- Generated vs hand-listed: do not add `part:` or `plan:` items to items.json; do not hand-edit lines that models.mjs generates in recipes.json/items.json.
- Quest items (`quest` field) are taken back on abandon; a quest that gives an item must set it.
- Rewards `items` go to storage, not cargo (so a full hold cannot lose them).
- Towed salvage: `towDelivered` cuts a wreck into structural plate (`isStructural`, `towTuning().salvage` share) and credits to storage; modules are not salvaged. A pod is emptied into storage.
- Profiles from Postgres come back with jsonb key order changed; never depend on object key order in profile data.
- Market prices drift on a 4-hour cycle (`MARKET_CYCLE_MS`) per station and recover over 30 min; tests that sell repeatedly must account for saturation.
- Pilots.ts and Quests.ts are large: read the class method list (`grep -n "^  [a-z]*(" file`) and one method, not the file.

## Mining: work and keep (server/src/game/Mining.ts `extract`, data/mining.json)

Mining has two separate sides (Kieran, 2026-11-05):

- **Work** sets how often chunks come. A hit works `damage × tool.yield × work ÷ damagePerUnit` rock units (96). The rock loses every unit worked, kept or not. A chunk is thrown every 5 to 10 units worked (`chunkUnits`, rolled per chunk).
- **Keep** sets how much ore is in each chunk. Every unit worked is a dice roll against its keep (Kieran, 2026-11-05: "make every possible mine chance be a dice roll"), on the rock's own seeded RNG so a run replays the same. A failed roll is lost: the rock loses the unit all the same. A full keep (a laser at its grade) needs no roll. The averages are the keep, as before; only the variance is new. A drop whose rolls all failed is skipped, so no chunk is empty; the less a tool keeps, the more drops are skipped (guns on Mk II rock skip about a third). When the rock is spent, whatever was kept is thrown with it. Mining XP is per unit kept.
- **The strike effect.** Every hit on a rock that rolls shows a mining strike on the client: a burst of rock dust and grit, distinct from a shell's plain spark (`client/src/rendering/weapons/MiningStrikeFx.ts`). No bytes are sent for it: the client draws it from the shell or beam it already sees strike the rock (the rock-bytes audit removed the per-hit spark and `projectileHit`), so it plays on every mining hit whatever the roll. The richer look on a success comes from data the client already has: a chunk of ore thrown out of the rock gets a brighter dust puff where it appears.

**Mining lasers** (they have a grade) use `laserGap`, indexed by the laser's grade minus the rock's tier (the system's Mk), clamped to +2:

| Gap | +2 | +1 | 0 | −1 | −2 | −3 or less |
|---|---|---|---|---|---|---|
| work | 1.3 | 1.2 | 1 | 0.85 | 0.7 | can't mine ("fit a better one") |
| keep | 1 | 1 | 1 | 0.8 | 0.6 | |

Every laser mines independently. The crowd mechanic (`crowd`, `kByGap`, `crowdFactor`, "works best with N lasers") is gone: four lasers mine four times as fast. **Power is the limit on laser spam.** A Mining Laser draws 30 a second (it was 12) and a Bore 40 (was 18). On the pool core, `payMining` records the share of their draw the lasers got (`ShipState.mineShare`), and `stepMiners` cuts by it, so lasers beyond what the generators can run brown out. Before this change the pool's share was ignored: a laser cut at full strength whatever it got, unless it got nothing at all. The ports core already cut by fulfilment, and its port rates were not changed.

**Guns** are any tool that is neither a mining laser nor a `mining: true` tool (charges, the siphon). They use `guns`:
- They mine hardness-1 rock only. On anything harder they say "fit a mining laser". Their tool hardness only decides which harder ores and gem seams inside soft rock they can take.
- Every gun kind has the same normalised yield, 0.6 (the EMP has 0). A starter's 112 damage a second works about 0.7 units a second, the same as a Mk I laser. A miner's damage on the rock is tracked as a leaking one-second sum. Above `refDps` (112) the pace grows only with the square root of it: `work × √(refDps ÷ dps)`. A gunship with twice a starter's damage works a rock about 1.4× as fast, not 2×.
- Keep = `keep` (0.32) for the common ores (`common`: iron, nickel, silicate, ice). Other ores and gems keep `keepOther` (0.5) times that. All of it is multiplied by `keepByTier[rock tier]` (Mk I 1, II 0.4, III 0.15, IV 0.08, V 0.05).

Why the numbers: guns keep about 30% of a Mk I Chondrite, so a Mk I laser gets about 3.3× the ore from a chunk cadence that is the same. A Mk I laser one or two grades behind still beats guns by 6× or more. Rocks hold `size × 0.15` units and `size × 30..120` HP. Guns work a rock out after about `size × 24` damage, so they mine a rock out before they break it.

## Notes (moved from DEVELOPMENT.md and the old engine-map)
- **Saves and backups**: profiles are `data/profiles/<accountId>.json` (gitignored, kept by deploys) in dev and the JSON store; production uses the Postgres store. Each JSON write goes to a temp file, is flushed and renamed into place; a failed write leaves the last good one. The first save of an account each day copies the previous one to `data/profiles/backups/<accountId>/<yyyy-mm-dd>.json`, keeping 7 days (`BACKUP_DAYS` in `JsonProfileStore.ts`); a save that will not parse is moved aside (`<id>.json.broken-<time>`) and the newest backup is loaded. Manual rollback: stop the server, copy a backup over `<id>.json`, start it. See `docs/audits/server-robustness.md`. Guests get a fresh profile that is never saved; `migrateProfile` upgrades old saves. A logged-in pilot's ships (active and hangar) are in the profile (`data/ships/players/` is a leftover, unused).
- **Profile lifecycle** (`Pilots`): login, autosave every 30 s, save on dock/logout/shutdown, credits, XP and levels, cargo vs shared storage, item actions, hangar refits that use only owned parts, the rebuild bill, death, skills, quest rewards (`grant`). It emits events (`onEvent`) that quests listen to. One session per account: `GameServer.loginPilot` saves and signs out any other connection on the account before loading the profile.
- **Mining, pods, services**: ore breaks off as chunks tagged with their miner; pods pull towards ships with room; stations refine, fabricate (instant or queued) and trade (`Mining`/`LootPods`/`StationServices`). How mining yields is below.
- **Levels and money** (`levels.ts`): XP to a level is `75 x (level - 1)^3`; grade licences (`material:*`) need a level (`GRADE_LEVEL`: Mk II 5, III 10, IV 15, V 20); higher grades take more plates per cell (`parts.platesPerAreaByGrade`), more ore, longer refining and fabrication (`parts.timeByGrade`). Credits are scarce by design: quest and ribbon credits are small, bounties pay `CREDIT_SCALE` of old rates, ore-run and supply-drop bounties scale through `payOut`, bosses pay the most.
- **Structure vs modules** (`econ/salvage.ts`): structure (hull, armour, conduits, cargo holds) is never fabricated or kept as an item; placing it in the hangar costs its refined materials (`placeCost`), and items arriving otherwise are turned into materials (`Pilots.give`, login, enemy salvage). Modules are fabricated and kept as items. Refining always takes time (`recipes.json` refining `time`) in a per-station refinery queue separate from the fabricator's (`refine:<id>` jobs). The fabricator never refines on its own: it says what is short.
- **Hangar** (`server/src/game/Hangar.ts`): Save builds what it can (modules from storage, structure from materials); edits lose nothing. Build (`slotBuild`) puts a slot on order (`ShipRecord.auto`); each second `Hangar.tick` -> `work` fabricates missing modules (`StationServices.makeFor`) and refines short materials from storage ore (`refineFor`), at this station, else home, else any with the service; `fill` fits arrivals. Scrap (`slotClear`) breaks parts down with `salvageParts`: 70% of minerals back as raw ore (`SALVAGE`), every component in full; `scrapItem` does the same for modules. Priority: `ShipRecord.rank` and `paused`; `orderRanking` orders `tick`'s work; `slotOrder` holds, resumes, moves to front (`top`) or calls off (`cancel`, refunding). Jobs the hangar queues carry `for` and `slot`. Station jobs can be held, resumed, moved to the front or called off (`job` message, `StationServices.jobAction`; a held job keeps its progress `heldMs`; calling off refunds unfinished runs, and calling off an order's job also holds the order). **Order plans** (`econ/orders.ts planOrders`) cost every unfinished slot down to ore in priority order; the client runs the same planner (`PilotState.orders`) for the Ships tab and the refinery/fabricator Waiting lists.
- **Death** (`Pilots.onDestroyed`): cargo drops in a pod; the ship's salvage goes to storage (70% of minerals, all with an insurance bond, plus every component); its slot becomes all ghosts, `lost` and on order, unflyable until whole (`Hangar.tick` announces); the pilot respawns in a loaner (free starter, `loaner: true`, cannot be refitted).
- **Safeguards**: the hangar fits a part only if its material and function are licensed (`Hangar.licensedFor`), however it was got; a plan the pilot knows builds as designed up to the plan's count. `Pilots.payRepair` (see weapons notes).
- **Quests** (`data/quests.json`): story, side stories, metallurgy, guild, shipwright and trader chains, generated station bounties (same for everyone per 30-minute window). State in `profile.quests` (active, done, known leads, dialogue flags). Counted steps advance on events; travel/dock/visit/level/refit/deliver steps are checked twice a second. Client: `ui/QuestUI.ts` (tracker, contracts tab, pilot log L, skills K); markers in `NavMarkersUI`; objective guide (`client/src/ships/route.ts`, `ui/GuideUI.ts`: routes through gates, rifts, down to planets; autopilot G).
- **People and dialogue** (`data/people.json`, `server/src/game/People.ts`, shapes in `econ/dialogue.ts`): each lives at a station or a point in a system (surface included; fly within 900 and press X: `handleInteract` in net/handlers/flight.ts asks `People.nearby` first); `moves` relocate someone while a condition holds. Sent as `people` with a mark; drawn by `ui/PeopleUI.ts`. Conversations run on the server and show in `ui/DialogueUI.ts` (1-9 answer, Space skips typing, Esc leaves). Line kinds: `say`, `ask`+`choices`, `if`, `offer`, `reveal`, `give`, `flag`, `advance`, `fight`, `end`. Step kinds: `talk` (person, lines, take, give), `visit`, `boss` with `arena`+`person`, escort `ward`, craft `teach` (a job's own recipe). Nothing is forced: jobs with a `person` are only offered by them; `starter` jobs are leads from the start; any job can be abandoned. Calls over comms use the same lines. Someone aboard a ship (`craft` in people.json) is spawned at world start (`GameServer.spawnPersonCraft`), pinned, invulnerable, a ward. Content lore follows `docs/lore-canon.md`.
- **Records** (`data/codex.json`, `econ/codex.ts`, `server/src/game/Codex.ts`, pilot log Records tab): lore as found documents, each attributed (`source`). Found when an `unlock` condition holds (checked twice a second), by a `{ codex }` line, a job's `rewards.codex`, an item's `codex` entering the hold/storage, or a wreck's log (a derelict with `log: { codex }` files it for a pilot within 900 of the hulk or on the salvage kill; a broken-up hulk cannot be read until towed back). Saved as `profile.codex` (`found`, `fresh`); toasted via strings.json `codex.found`. Admin: `/codex [name] id|all|clear`.
