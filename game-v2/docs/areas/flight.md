# Flight & physics
How a ship moves: `stepFlight` turns inputs plus `ShipDerived` (thrust, mass, inertia, drive) into velocity/angle changes with PD turning, friction, boost, gravity wells, the jump drive, the Burst Strafer dodge and cargo/tow mass. `stepShipPhysics` wraps it with terrain collision and rounds the result to snapshot precision so the server, the pilot's client prediction and the replica shadow land on identical numbers. All of it is pure, shared code in common/src/ships.

## Public interface
- `stepFlight(body, input, derived, tuning, boost{charge,drainRate,load?,tick?}, k) -> FlightResult`; call `stepShipPhysics(body, input, derived, tuning, boost, gravity, jumpBoost, hazard, terrain)` instead; never quantize by hand (`quantizeShipBody`).
- `FlightBody` {x,y,vx,vy,angle,angVel, jump?, jumpScale?, cargo?, dodge?, dodgeDir?}; `FlightControls` {forward, backward, left, right, boost, targetAngle, helm?, strafeLeft?, strafeRight?, jump?, jumpDist?, dodge? (boolean)}.
- Counters on the body (jump, dodge, dodgeDir) are the whole feature state and ride keyframes/snapshots.
- Wire side of the input bundle: protocol.ts input message + binary flags2 (`encodeInputBinary`: strafeLeft/Right, helm, jump, targetTick, dodge; 0x20 and 0x80 free); `CTL` bits in replica.ts; server `Input.*` ECS arrays (GameServer `applyInputToEntity` and `releaseControls`).
- Jump: `jumpDriveStats`, `pilotJumpStep` (jumpFields.ts) wrap a step with field boosts; both ShipBridge and ShipClient use it.

## Invariants
- Deterministic: no Date.now, Math.random, I/O, imports from client/server. Same inputs -> same body, bit for bit.
- Server and client MUST feed `stepShipPhysics` identical data: body fields, controls, charge/load/tick, gravity, rangeBoost, hazard (EMP via `withEmp`, cold via `withNumb`), terrain. Divergence shows up as rubber-banding.
- Quantization: results rounded to `SHIP_PRECISION` (pos 2, vel 4, angle 5, angVel 6 decimals) after every step; cargo to `CARGO_PRECISION`. Never carry unrounded state across a tick.
- Cargo (hold + tow load) is part of the body (`body.cargo`), not stepped; flight divides thrust over mass + cargo (`accelAlong`).
- Losing parts never makes a ship quicker: flight divides by `fullMass`/`fullInertia`; `derived.drive` scales a wrecked ship's engines.
- A jump burn disables steering, thrust, friction and gravity; a dodge doesn't start while the drive spools (and nothing steps during a burn).
- `flightSignature(d)` equality = identical flight; changing what flight reads from `ShipDerived` must stay inside it.

## How to extend
Add a flight-affecting ability (dodge-style):
1. Part and `ShipDerived` key: see [ship-parts](ship-parts.md) (the feature block in common/src/ships/rebuild.ts).
2. Feature file `common/src/ships/<x>.ts`: tuning + pure `stepX(counter, want, able, t)`; keep state as ONE integer on `FlightBody`.
3. flight.ts: add the field to `FlightBody` and the control to `FlightControls`; hook into `stepFlight` at the matching banner (read only that slice).
4. Controls plumbing, ALL copies: protocol.ts input type + binary flags (bump `PROTOCOL_VERSION`, `npm run wire:bump`), the input list in common/src/network/inputFields.ts (`INPUT_BOOLS`/`INPUT_NUMBERS`) and GameServer `applyInputToEntity`/`releaseControls`, `controlBits`/`flightControls`/`CTL` in replica.ts, ShipBridge.stepMovement (body read + input), ShipClient.predict (body + `player.x` write-back), client input collection (`ui-hud-input`), `GameState.ts` pilot-row parsing (`player.dodge` etc.). The audit flags these hand-copied lists as the top drift risk.
5. Keyframes/snapshots: pilot row extras (`pilotExtras` in strafer.ts, used by SnapshotBuilder.systemRows, net/SnapshotBuilder.ts).
Tune: edit data/ships/tuning.json, never inline constants; respect the `xxxTuning` default pattern.
Add a velocity source (gravity, hazard): through `FlightConstants`, not in the bridge.

## Gotchas
- Both sides build their `FlightControls` with `buildFlightInputs` (common/src/ships/flightInputs.ts). The `FlightBody` (cargo, dodge, jump counters) is still copied by hand on each side: `ShipBridge.stepMovement` and `ShipClient.predict` (`body = {...}`). A new body field missing on the client side is a silent desync: add it to both copies together.
- `replicaStep` (shadow on the server, Replication.ts) uses `FULL_CHARGE`, `drainRate 0`, and the control bits only: anything not in `CTL`/keyframe (jump distance, cargo, cursor) is not replicated, and a mismatch forces a keyframe. `replica.ts` header says clients replay too; at this time no client code calls `replicaStep`.
- Jump landing distance isn't replicated: the burn start triggers a keyframe.
- Berthed pilots skip prediction (`ShipClient.predict` early return).
- The Tow Beam's towed object is moved by the server only (server/src/ships/features/tow/Towing.ts) and never predicted; only its load (cargo mass) is.
- Never import collide.ts hit tests for gameplay damage outside the weapons code path; use the same functions server and client.

## Notes (moved from DEVELOPMENT.md and the old engine-map)
- **Cargo mass**: a hold's contents have mass (`ItemCatalog.mass`: the item's `mass` in items.json, else `CATEGORY_MASS` by category x its volume; station storage weighs nothing). It rides on `FlightBody.cargo` (from `Pilots.cargoMass` each tick) and divides thrust and turning in `flight.ts` against the ship's own mass (`load.ts`), so the server, the pilot's prediction (snapshot `data[14]`) and replicas (keyframes carry it) fly the same load. `ItemCatalog.massOf(stacks)` is the hook for pay-by-weight jobs.
- **Stabiliser Anchor**: removed 2026-10-31 after playtesting ("lame"); protocol 16 took its input flag, CTL bit, pilot-row slot and keyframe slot out. Its id stays in the append-only wire dictionary. Design history: docs/design/build-archetypes.md §5 #4.
- **Burst Strafer** gives no thrust, only a dodge (reworked 2026-10-31: any way, stronger, short cooldown, energy-limited; no charges). The held `dodge` control (input flags2 0x40, replica bit `CTL.dodge`, key Space; `ShipClient.dodgeControl` latches a press, buffering one made during the cooldown) starts one burst of `strafe.ticks`. Its way is worked out inside the sim from the movement keys of that tick (`stepFlight` turns WASD or helm forward/back/Q/E into a ship-local vector; `chooseDodgeDir` quantises it to one of `DODGE_DIRS` = 32 ways; nothing held, or a way no strafer pushes: back the other way from the last dodge, else sideways, stronger side, right on a tie), so prediction, server and replicas agree without sending a direction. Each strafer pushes away from its nozzle (`StraferPart.push`, ship-local); a way gets the sum of their components along it. Next burst `strafe.cooldown` ticks after one starts (one a press). State is two integers (`dodge` counter, `dodgeDir` the last way, kept for the weave) carried in keyframes and the pilot's row after the charge groups (`pilotExtras`). A burst draws `demand` x each strafer's share along the way via `PowerUse.dodge`: first from the capacitor bank the strafer touches, then its circuit as an engine; short of it the push scales by the share, and a burst getting under `DODGE_MIN_SHARE` (0.25) on its first tick is refused (`refuseDodge`: no push, counter to the end of the cooldown). Numbers: `strafe` per model in models.mjs (kick 14 per cell, 12 ticks, cooldown 24, demand 700/s a cell = 140 energy a burst straight out).
- **Tow Beam** is server-side (`server/src/ships/features/tow/Towing.ts`): `{ type: 'tow', on }` (key U) takes hold of the wreck, debris or pod nearest the cursor (never a working ship: `ShipBridge.towable`); a spring tether (`towPull`) pulls it each tick. It is a part feature (`common/src/ships/features/tow/`, README there): its mass rides as cargo (the feature's `cargoMass`, summed by ShipBridge as `featureCargo`) so prediction flies the load, and the beam draws while it tows (`ShipState.tow`, the feature's `load()` in `gunLoad`); a ship's tow data is `derived.fx.tow`. In a station's reach `GameServer.towDelivered` salvages it (wreck/debris structure as plate via `tow.salvage` into storage plus a derelict's credits; a pod's contents into storage). Numbers: `tuning.json tow` over `DEFAULT_TOW`.
- **Jump drive** (J; `stepJump`, `jumpPhase`, `jumpBurnSpeed`, `tuning.json jump`): one counter (`ShipState.jump`, `FlightBody.jump`): ready, charging while held, burn, cooldown. Rides in player snapshots as `data[3]`, control as an input bit. Charging lets you aim but takes the engines and brakes the ship; releasing cancels with no cooldown. The burn flies along the nose at fixed speed (~70k units in ~3.5 s, then 15 s cooldown) with no steering, friction or gravity; guns don't fire and the ship passes through hulls. The client latches J until the burn starts; J again aborts; `client/src/ships/JumpFx.ts` draws charge rings, flashes, wake, streaks and the gauge, and the camera locks and pulls back. The proto repair key is U.
- **Stillstone fields** (`jumpFields.ts`; "lodestones" in code): a live one's field reaches `jump.lodestoneField` past its `size` (`lodestoneFieldRadius`), speeds the drive's cooldown and primes the next jump; scarred ones give `lodestoneScarredCharge`/`lodestoneScarredBoost` of that (fractional charge counted in whole ticks by tick number, `wholeTicks`; priming kept negative, `primeBoost`); dead and shattered ones nothing. Server, prediction and replicas all run it from `systemInfo.lodestones`.
- **Flight damage**: `rebuild.ts` gives every ship mass and inertia as built (`fullMass`, `fullInertia`: every part but unbuilt hangar ghosts) and a `driveFactor` (1 whole, ~0.7 at half its mass, ~0.35 down to a core and a few parts). `accelAlong`/`turnAccel` divide by them and multiply by the drive, so losing parts never makes a ship quicker. Ghosts travel in `shipSync.ghosts` so prediction agrees. The core's maneuver force (3) and gyro are unchanged.
- **Scale**: `cellSize` 24 (hulls 3x larger), thruster `thrust` 2.26 and `coreManeuverForce` 3 (doubled), `gyroTorque` 216 and `thrusterTorqueGain` 9 keep turn rates; `BULLET_SPEED` 48. Thrust direction stays screen-relative: force along the input is the sum of thruster projections, floored by `coreManeuverForce`; turning torque = core gyro + `thrusterTorqueGain` x side thruster torque about the COM. Mouse-steer and helm share one flight model (the `helm` bit is in every input). Collisions use shrunk convex pieces and an impulse along the deepest-penetration normal (`tuning.collision`).
- **Docking** (`conn.docked`): a docked ship sits at the station's centre (put back at `docked.exit` on undock); `Docking.dockedShips` (game/Docking.ts, rebuilt each tick by `dockingSystem`) lists them; GameServer keeps an alias to the same Set. Invulnerable, out of `canDamage` both ways, skipped by contacts, cannot fire (`ShipHost.sheltered`), left out of hostiles' and bosses' player lists. `ShipRenderer` hides docked ships; `ShipClient.predict` holds you at the station.
- Gravity wells (`centralBody.gravity`: strength, minRadius, horizon) are part of the shared step; crossing the horizon destroys a ship (The Maw, the Void Sector).
