# Ops, deploy & tools
How the game gets onto the user's shared VPS (space.brotherk3d.com), how it is backed up and watched, and the developer tooling around it: dev servers and ports, test commands, benches, profilers, still/screenshot renderers, update panels, notifications. The VPS is shared with the user's other projects (brotherk3d.service on :3001, mealmaker, Postgres, nginx site `brotherk3d`): never disturb them. No Docker on the box on purpose. Fly.io is retired; "live game" means the networked code and the VPS.

## Public interface
- `bash deploy/vps/deploy.sh` (from `game-v2/`): the only way code reaches the VPS. `WITH_SITE=1` adds the website (takes over `/`, game moves to `/play`); without it a running website is left running and keeps `/`. `bash deploy/vps/deploy.sh rollback [name]` / `releases`.
- Secrets live in `/etc/spacegame/secrets.env` (root-only, loaded by units via `EnvironmentFile`): `LOBBY_ADMIN_SECRET`, `SITE_SECRET`, `DATABASE_URL`. Created once by `remote-install.sh`; never print or commit them (look up with `sudo grep NAME` on the box only when needed).
- `OWNER_USERNAMES` (lobby, optional; not a secret): comma-separated usernames made the owner (the rank above admin) at every lobby start. Not set by `remote-install.sh` or the units: add `OWNER_USERNAMES=brotherk3d` to `/etc/spacegame/secrets.env` (or a drop-in for `spacegame-browser`) and restart the lobby. Removing a name doesn't revoke; that and one-off grants go through the lobby's `POST /admin/set-owner` with `LOBBY_ADMIN_SECRET` (web-accounts, Ranks). Owner-only tools: granting/revoking admin, acting on admins, deleting accounts, publishing posts, API tokens.
- Dev ports: game server 3000 (admin 3005), Vite 5273, site 5310, lobby 8787, native renderer 5311, monitor 8971.
- Data preserved across deploys: `data/{users.json*,users.db*,lobby,ships/players,profiles,telemetry,contributor,status,site,world,backups*}`. Everything else in `data/` is exactly what was shipped (`rsync --delete`).
- Backups: profile daily copies `data/profiles/backups/<id>/<date>.json` (7 days, `BACKUP_DAYS` in `server/src/profile/JsonProfileStore.ts`); world memory `data/world/memory.json`; nightly pg dumps (14 kept); pre-migration copies under `/opt/spacegame/data/backups-pre-pg-*`.

## Invariants
- Touch only `/opt/spacegame`, the `spacegame-*` units, the `spacegame` nginx site and its snippet. Always `nginx -t` before reload. Do not run SSH/deploy unless the user asked.
- Never print secrets; never commit `.env`. Production must not seed `admin/admin`.
- Git: never `checkout`, `restore`, `stash` or `reset` (huge uncommitted tree; the last deploy tarball `/root/spacegame.tgz` on the VPS is the recovery copy). Commit/push only when asked.
- Process hygiene: check the port before starting a dev server and reuse a running one; kill what you (or your subagents) start, by PID (`taskkill /T /F`), never sweep by port; never kill the user's Chrome (C:\Program Files\Google\Chrome) or processes under a live VS Code terminal.
- One headless browser per agent at a time, closed in a `finally`; no parallel shot runs; run test suites alone, not alongside a browser run; prefer native `npm run render` for stills.
- Panels: capture the "before" first; files `docs/panels/<YYYY-MM-DD>/<category>/<topic>-before.png|-after.png|<topic>.png`, no overlays on pixels, add one entry file in `docs/panels/entries/` and run `npm run panels:index` (see docs/panels/README.md; never edit `docs/panels/index.md` by hand).
- Send a Pushover note before long autonomous work, at milestones, and after a deploy.

## How to extend
1. **Deploy**: from `game-v2/` run `npm test` and a build check, then `bash deploy/vps/deploy.sh` (`WITH_SITE=1` for the site). Watch for `Deployed.`; check https://space.brotherk3d.com/; notify via `notify.mjs`.
2. **Add a systemd unit/timer**: write `deploy/vps/spacegame-<name>.service` (+ `.timer`), copy `spacegame-dbdump.*` as a model (hardening, `ReadWritePaths`, `EnvironmentFile=/etc/spacegame/secrets.env`); `deploy.sh` already scp's `*.service *.timer`; add `install -m 644` + `systemctl enable --now` in `remote-install.sh` (after the `daemon-reload`, guarded like the dbdump block).
3. **Add a secret**: add its name to the `for name in ...` loop in `remote-install.sh` (generated once with `umask 077`).
4. **Add a service to the monitor**: see the monitor row above.
5. **Add a bench/profiler**: `server/src/bench/<x>Bench.ts` (copy `tickBench.ts` header and flags); register an npm script in `server/package.json` if it should be routine.
6. **Fetch contributor notes**: `node scripts/contributor-notes.mjs --author <name>`; after implementing `--mark-done <id> --note "..."`.
7. **Postgres re-sync / switch**: `scripts/db/vps-sync.sh --verify-only|--dry-run|--replace`; full steps in `docs/ops/postgres-migration.md`.
8. **v5 design update** (PROFILE_VERSION 5, `common/src/econ/designUpdate.ts` `designUpdateShips`, run by `migrateProfile`; owner's call, 2026-11: ships move to the ports power core). Only ships change: XP, level, skill points, credits, storage, skills, quests, plans, recipes, licences, reputation and the codex stay for everyone. Per account (by username) `data/ships/designUpdate.json` maps hangar slots and saved designs (0-based) to a blueprint: `remakes/<file>` (the hand-made player remakes in `data/ships/blueprints/remakes`: the deploy ships that folder, the server loads it apart from the plan library, so it's never sold, learned or listed in the fabricator; it is on the dev F9 swap) or a library id with `stock: true` (the current library ship replaces the old). A slot whose save still matches its `was` (name and part count as saved, before any older migration) gets the remake in its place: the remake's name, full HP, the plan kept (a stock swap: the library id), its ammo loadout trimmed to the crates its new guns take; one that wasn't whole (lost, or still being built) comes back whole too (owner's call, 2026-11-07: "just give them built ships"), nothing refunded for it. A design is remade in its place the same way. Anything else (not mapped, changed since, remake missing, loaners) is broken down: built parts to storage as raw materials in full (`salvageParts` at 1) plus socketed gems (nothing for a loaner, a ghost part or a part at 0 HP). An account marked `"wipe"` (brotherk3d), one not in the mapping, or one left with no ship gets a fresh starter (the release's `sparrow-t`) in slot 1, its rebuild debt forgiven (and then a stock Sparrow T gives back only the parts beyond the starter's); one left with only unfinished ships gets a loaner. Everyone: docked at home, hold moved to storage, `plan:*` items dropped, ship-bound fabricator jobs detached (kept, for storage), wreck marker cleared, and a one-time login toast: "Your ships have been rebuilt for the new power system: ..." for swaps, the wipe wording ("your hangar has been reset", "broken down into storage", the refund listed) only where something was wiped. A job at main_02's build/fly step whose ship went goes back to its "start the Prospector" step at login (`Quests.rewindShipSteps`). The game runs the same migration, with the same mapping, on any save below v5 at login (`Pilots.login` passes `conn.username`), so anyone the bulk run misses is swapped, not wiped, when they next sign in. Production's saves are at v2 and v4 (none at v5), so this is the v5 step itself rather than a v6 on top: a v6 after a v5 wipe would have nothing left to swap. The bulk tool is `scripts/db/designUpdate.ts` (usernames from `users`, joined on `profiles.user_id`), run on the VPS by `scripts/db/vps-designupdate.sh`: JSON on stdout (kept in `/root/design-update/report-<mode>-<time>.json`), a line per player on stderr (swapped, wiped and why, refund, the slot flown, XP/level/credits/skill points before -> after). Run it with the deploy, as root on the VPS unless noted:
   ```bash
   # 1. Back up the database first. With the old release still installed, stop the game server (it saves every pilot
   #    as it stops), then dump the two tables and keep a copy of profiles inside the database, while every save is pre-v5
   systemctl stop spacegame-server
   ( set -a; . /etc/spacegame/secrets.env; set +a
     umask 077; d=/opt/spacegame/data/backups/db; mkdir -p "$d"
     pg_dump --no-owner -t profiles -t game_docs "$DATABASE_URL" | gzip > "$d/pre-designupdate-$(date +%Y%m%d-%H%M%S).sql.gz"
     psql "$DATABASE_URL" -c 'CREATE TABLE profiles_pre_designupdate AS SELECT * FROM profiles' )
   # 2. From game-v2/ on this machine: deploy (bash deploy/vps/deploy.sh). It installs /opt/spacegame/data with the
   #    mapping, the remakes and the new starter, and starts the server again: stop it straight away (anyone who signed
   #    in meanwhile was updated at login, by the same migration, and is skipped below)
   systemctl stop spacegame-server                      # a running server saves over what the update writes
   # 3. From game-v2/ on this machine: dry run, and read it (writes nothing)
   scripts/db/vps-designupdate.sh --dry-run
   #    Check: brotherk3d "wipe" with a fresh starter; Xire slots 1-2, I0lOl0I slot 1, Pig_Benis slots 1-2 + design 1,
   #    YuhboiFlappysack slot 1 all "swapped"; no "changed since" or "remake missing" (one means that save changed after
   #    2026-11-07 or a remake didn't ship: fix designUpdate.json and redeploy, or accept the wipe for it); and every
   #    player's xp, level, credits and skill points the same before and after
   # 4. Apply (one transaction; rows at v5 skipped)
   scripts/db/vps-designupdate.sh --apply
   # 5. Start the game server again
   systemctl start spacegame-server
   # 6. Tell the players whose ships were remade (and the owner): the lobby's /admin/mail, from "system", one each
   ( set -a; . /etc/spacegame/secrets.env; set +a
     for u in Xire I0lOl0I Pig_Benis brotherk3d; do
       curl -s -X POST http://127.0.0.1:8790/admin/mail -H "Authorization: Bearer $LOBBY_ADMIN_SECRET" -H 'Content-Type: application/json' \
         -d "{\"to\":\"$u\",\"body\":\"The mechanics have updated on ships, rather than wiping your ships we've had it remade- thanks for playing!\"}"; echo
     done )                                             # each prints {"success":true,"sent":1,"to":"<name>"}
   ```
   (The `pg_dump`/`psql`/`curl` lines put the URL or secret on a command line for the moment they run: fine on this box as root with no other users signed in; otherwise use the PG* + PGPASSFILE shape of `deploy/vps/spacegame-dbdump.sh`.) Undo before anyone plays: `systemctl stop spacegame-server`, then `psql "$DATABASE_URL" -c 'BEGIN; DELETE FROM profiles; INSERT INTO profiles SELECT * FROM profiles_pre_designupdate; COMMIT'` and deploy the previous release (`deploy.sh rollback`), or the restored saves are updated again at login. Drop `profiles_pre_designupdate` once the update has settled. Locally: `DATABASE_URL=... npx tsx scripts/db/designUpdate.ts --dry-run` (default game data: this repo's `data/`). To change who gets what: edit `data/ships/designUpdate.json` (and add remakes to `data/ships/blueprints/remakes`); `common/src/econ/designUpdate.test.ts` checks every id it names is found.
9. **Friends move to the lobby** (2026-11). Friends, requests and the saved status now live per account in the lobby (`friend_lists` table), not in each game server's `social` document. Nothing to run by hand: deploy the lobby and the game server together; the lobby makes `friend_lists` at start (as `schema.sql`), and the game server, at its first start, sends the production `game_docs` row `social` (if there is one) to the lobby's `/admin/friends/import` and marks the row `movedToLobby` (kept, not deleted). Idempotent: later starts see the mark and send nothing; a second import adds nothing. Check after the deploy: `journalctl -u spacegame-server | grep Friends` shows "moved this server's friends to the lobby: N accounts, ..." once (or nothing, if production had no friends yet), and `journalctl -u spacegame-browser | grep Friends` the matching "imported" line. If the lobby logs "[Friends] off" (its database user can't make the table), apply `server-browser/schema.sql` as the tables' owner and restart it; until then friends show "unavailable" in game and the game server retries the move every 15 s. Look at the old row: `psql "$DATABASE_URL" -c "SELECT data FROM game_docs WHERE key = 'social'"`; the new rows: `SELECT * FROM friend_lists`. Dev does the same with `data/profiles/_social.json` into `data/lobby/friends.json`.
10. **v6 field update** (PROFILE_VERSION 6, `common/src/econ/fieldUpdate.ts`, run by `migrateProfile` at login for any save below v6; docs/design/field-fabrication.md section 8). Nothing to run by hand. Repair kits and insurance bonds (storage, hold, crafting jobs) become repair-bank deposits (their old recipe inputs, `RETIRED_KITS`), the free part starts full, loaner records are dropped (a flown loaner gives way to the lost ship, ghosts kept and owed to the bank, else a fresh starter), the quick bar's kit slots clear, and one login notice says so. `scripts/archive/econ/retireKits.mjs` already rewrote the data (drops, quests, vendors); the bulk design-update tool still reports v5 saves only, since the v6 step runs at login.

## Gotchas
- `set -euo pipefail` in `remote-install.sh`: a failing test inside `x=$(cond && ...)` or a bare `cond && cmd` as the last command can abort the deploy mid-swap with services stopped. Existing lines use `x=$([ ... ] && echo 1 || echo 0)` (the `|| ` makes it safe); keep that shape, or use `if`.
- The units are stopped before the directory swap and started at the end: a failure between leaves the game down; re-run the script after fixing, or `deploy.sh rollback`.
- `nginx-spacegame.conf` is installed only if the site file is missing (certbot edits it): put routes in `nginx-spacegame-game.conf` (refreshed every deploy), never in the site file. Inside an `if` only `return` (the socket goes `return 418` -> `error_page 418 = @spacegame_ws`).
- Vite node stubs (`fs path os url zlib` -> `client/src/nodeStubs.ts`) mean a server module that does real file I/O breaks the sandbox bundle.
- Render daemon: a leaked tab lease blocks every later `shoot.mjs` run until `LEASE_MS` (20 min) expires; always close/return your tab; check for orphaned "Chrome for Testing"/`--headless` processes by executable path after stopping agents (three parallel agents once left about 30 at 100% CPU).
- The VPS still allows password logins for root (flagged to the user, unchanged).
- Production uses Postgres since 2026-10-31 ~14:33 via the systemd drop-ins `spacegame-{browser,server}.service.d/postgres.conf` (not in repo units; the deploy leaves drop-ins alone). Pre-switch backups: `/opt/spacegame/data/backups-pre-pgswitch-20261031-143323`. The deploy installs the nightly `pg_dump` timer `spacegame-dbdump`. `docs/ops/postgres-migration.md` has the rollback steps.
- Windows host, Git Bash: use forward slashes and `/dev/null`; temp files go in the session scratchpad.

## Sim tools (dev only: network simulator, overlay, Rockery spawns)
Dev builds only; nothing here is in a production build (the client code sits under `import.meta.env.DEV`, the server ones are installed only when `NODE_ENV` is not production). Everything starts off.
- **Open it**: in the dev client press **F7** (also a button in the F8 render panel). Guests are admins on the dev server, so every button works.
- **Network simulator** (this client's connection, both ways): tick *Enabled*, then the sliders: *Ping* (round trip, split half each way), *Jitter* (+/- on each trip; never reorders, it is TCP), *Loss* (% of inputs going out and snapshots coming in; everything else is only delayed). Untick to go back to the real connection. Code: `client/src/dev/netSim.ts` (seeded, tested), hooked in `client/src/network/NetworkManager.ts` (`netSim`, null unless the dev panel installs it).
- **Overlay**: *Overlay* button or **Shift+F7**. In the world per ship: cyan outline = ST (confirmed pose), yellow = PT (client's stepped pose), white ring = where it is drawn, a line between ST and PT (green < 2 units, yellow < 20, red above), red arrows for corrections as they land. A counters panel beside the tools panel: corrections/s, re-steps/s, hash misses/s (a dash until Stage 3), correction mean/max, prediction CPU a frame, drawn-hit and real-hit rates, input-to-screen estimate, mode name. Checkboxes switch each part. The overlay reads only the `SimOverlaySource` interface (`client/src/dev/simOverlay/types.ts`: ships with `pt`/`st`/`drawn`, `counters()`, `corrections()`, and the optional `mode()` / `extras()` hooks for the C2/C3 modes). Today's adapter is `gameStateSource.ts` (reads GameState's reconcile stats, `selfPoseAt`, `ShipClient.replicas.at`, the hit counters; corrections are detected by a change in the reconcile numbers, so two in one frame count once).
- **Rockery buttons** (the guest joins the Rockery on the dev server; *Warp to Rockery* otherwise): *3/5/10 drones* (a Helios drone pack 1200 units ahead), *Halberd/Arrow/Drum* (a still dummy beside you), *+1..+4 bots* (bot players on random flight, 4 at a time; pick calm/mid/twitchy and *shoot back*, which makes them fire at you), *Clear everything spawned*, *List*. They send `/rockery ...` chat lines (`server/src/bots/rockeryTools.ts`), so you can also type `/rockery bots 2 twitchy shoot`. The bots are real simulated players (`ClientDriver`, god mode) flown by the `random-flight` task.
- **random-flight task** (`server/src/bots/tasks/randomFlight.ts`): sharp turns, boost bursts, hard stops; `twitch=calm|mid|twitchy|0..1` sets the input-change interval (about 4 s calm down to 0.2 s twitchy), `boost=`, `stop=`, `leash=`, `seed=`, `shoot=1 range=`. Also `/bot spawn random-flight 2 client twitch=0.9`. "Fire" is the controls' `mine` flag (right mouse): `Controls` has no primary-fire field.
- **`/rockery bots ... near`** (the panel's *stay near*, on by default): the bots keep within about 900 of you wherever you fly (RandomFlight `homeOf`), so they stay in the demo.

### Prediction modes (Rockery, F7)
C3 is the game's prediction in every build (client/src/predict/: `Prediction.ts` makes it from Game.ts, `modes.ts` the registry and `DEFAULT_MODE`, `ptst.ts` the PT/ST layer, `contacts.ts` its contact pass, `shipKinds.ts` ship kinds and the level of detail, `world.ts` its adapter over the tick layer; how it works: docs/areas/networking.md "Other ships: the PT/ST layer"). The Sim tools switch it live to the dev-only alternatives for comparison (`client/src/dev/predict/`: `PredictController.ts` the switch and the dev measures, `hitTally.ts` the hit numbers). Drawing only: the server, the tick layer (hits found, checks, your ship's step and inputs) and every other client are the same in every mode; the one hook in the game is `GameState.drawMode` (`client/src/state/drawMode.ts`), read by GameState.interpolate/ownDrawTick and WeaponFx's shell timelines.
- **Run it**: dev client (`npm run dev:client`, dev server), F7. *Warp to Rockery* if you aren't there; *5 drones* and *+3 bots* (stay near ticked; twitch mid or twitchy). Network simulator: tick *Enabled*, *Ping* 100-200, *Jitter* 10-20. Shift+F7 for the overlay. Then the *Prediction mode* buttons A/B/C1/C2/C3 (live; switching resets the mode's counters). `?predict=C2` in the URL starts in a mode, `?simOverlay=1` with the overlay on; `window.__simTools` (predict, overlay, net, read()) for the console.
- **A** interpolated (the drawing before C3): your ship predicted; every other ship at the interpolated render tick. Overlay: other ships drawn far behind where your shells meet them (*drawn vs ST* hundreds of units at 100-200 ms).
- **B** prediction off (drawn): your ship and shells at the render tick too. Everything you see agrees (gaps of a few units) but *input to screen* is the round trip plus the interpolation delay (350-500 ms): the controls feel late.
- **C1** AI ahead: ships flown from their decisions (drones, AI pilots, custom enemies; not bosses) stepped ahead to where your shells meet them (Timeline 'ahead', AHEAD_BACK behind your shells), their shells with them; pilots stay interpolated. Drones line up; bot players don't.
- **C2** PT/ST rubber band: every other ship on a PT layer at your tick (pilots on their last input held, AI on its decisions). Each snapshot hashes ST (the replica layer at the confirmed tick) against the PT recorded for that tick; a miss re-steps that ship once from ST to now and eases it from the old PT to the new over *C2/C3 ease* (default 150 ms). Overlay rows: PT ships, ST checks/s and match %, re-steps/s, re-step ticks/s, mean correction, re-step and PT CPU a tick.
- **C3** (the game's) C2 plus the touch register: ships a mispredicted one touched after the confirmed tick (the PT steps' contact events), or that its new path touches, are re-stepped with it (*of them touched*). PT contacts are the server's pass on PT states (RealContacts: a collision between predicted ships is no correction unless an input was mispredicted); AI ships are never pushed in PT (their decided path), your own ship pushes as a fixed body. Overlay extras: *PT snaps/s* (corrections of 400 u or more, not eased), *PT left out (LOD)* (ships beyond `PT_TUNING.reach`, drawn interpolated).
- **C2/C3: the rest of the world on PT too** (track C; registry `client/src/predict/ptKinds.ts`, the game's set `client/src/predict/worldKinds.ts`): bosses (`predict/kinds/bodiesKind.ts`: the replica layer at their PT tick, hashed each tick, eased on a miss), homing shells and mobs (`guidesKind.ts`: GuideRunner forks stepped to your tick), boss and custom-enemy moves (`movesKind.ts`: MoveRunner forks; their telegraphs and beams drawn as the body's PT tick reaches them, late ones started that far in, `predict/late.ts`; their straight shells drawn ahead, taken back if a re-fork doesn't have them). Other ships are read past the confirmed tick through `predict/aheadReads.ts` (the ships layer's PT, or a pilot held on its last input), never by stepping them on the replica layer. Overlay rows: *drawn vs ST: bosses*, *PT bosses / shells+mobs / boss moves: ST match*, *looks+shells ahead*, *world kinds CPU / tick*. Other ships' gunfire (pilots, drones) is not stepped ahead: the server decides when they fire and doesn't say until it has (their shells are drawn at the owner's PT tick from their fire records). Headless numbers: `server/src/net/decisions/ptWorld.test.ts` (PT_DEBUG=1).
- **Overlay rows for every mode**: *drawn vs ST: pilots / AI* (sampled 4 times a second: where each ship is drawn against its confirmed state at the tick your shells are drawn at, mean gap and % within half its radius), *strikes on target* (the same at each drawn strike of your shells), *hit agreement* (drawn strikes against told hits by shell; low in every mode, a still dummy included at about 45 %, so it measures how hits are told more than prediction; open).
- **Numbers by script**: `node scripts/boss-shots/predict-demo-steps.mjs <gamePort> > steps.json` then `node scripts/boss-shots/shoot.mjs http://localhost:<vitePort>/ out/predict @steps.json` (env MODES, PINGS, JITTER, LOSS, SECS, TARGETS=drones|bots|both|dummy, SHOTS, ZOOM): a guest strafing the traffic, each mode at each ping, `window.__simTools.read()` per run and a shot with the overlay. Panels: docs/panels/2026-11-06/predict-modes. Tests: `npx vitest run client/src/predict client/src/dev server/src/net/causes/ptContacts.test.ts`.
- **Crowd cost**: the crowd bench's probes run the game's prediction too (`server/src/bench/crowd/probe.ts`, `Probe.pt`, CPU apart from the tick layer's: the *probe PT* lines): `npm run bench:crowd -- --n 20,50,100 --layouts ball,spread`; `--pt-reach 1e9` lifts the level of detail, `--pt 0` turns PT off. From a worktree, run it with `TSX_TSCONFIG_PATH` pointing at a scratch tsconfig that maps `@space-game/common` to the worktree's `common/src`.
- **netTable bench**: `npx tsx --tsconfig ../scripts/net/tsconfig.json src/bench/netTable.ts --only mother,pirates,crowd-20 --secs 5` from `server/`. Its ship pool uses library ships (halberd, sunspear, wisp, ports dev ships), not the retired lancer/hammerhead/corsair.
