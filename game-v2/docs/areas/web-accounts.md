# Website, lobby & accounts
Three cooperating services. The **lobby** (`server-browser/`) owns accounts and sessions, keeps the game-server registry, and answers each server's heartbeat. The **website** (`site/`) is a server-rendered Node + TypeScript site (updates feed, suggestions, shoutbox, pilots/leaderboards, account pages, admin panel, an authed posting API, and `/play` which serves the game client signed in). The **game server** talks to the lobby through `server/src/auth/LobbyAccounts.ts` (it never stores accounts itself). The site has no accounts of its own; it signs in through the lobby and keeps the lobby session token in an HttpOnly cookie. Postgres is live in production for accounts, sessions, profiles and rankings (see `docs/ops/postgres-migration.md`; the JSON stores remain the default and dev backend).

## Public interface
- Lobby HTTP: `/auth/*` JSON POSTs (cookie-less; token in body/`Authorization`), `POST /register` heartbeat, `GET /list`; `/admin/*` guarded by `LOBBY_ADMIN_SECRET` (constant-time compared; wrong or empty is 403).
- `UserStore` (accounts/types.ts) is the contract all backends and `LobbyAccounts` implement; add a method to all of them plus the Postgres test.
- `SiteStore` (site/src/store/types.ts) likewise for JSON/Postgres.
- Site posting API: `Authorization: Bearer sgs_...` on `/api/v1/posts|uploads|preview|me`.
- Session sharing: `/play` puts the lobby session into `localStorage.authToken` before the game loads, so site sign-in = game sign-in (Game `resumeSession`).
- Deleted accounts: lobby heartbeat reply -> game server deletes profile and ranking entry.

## Invariants
- Accounts live only in the lobby store; the site and game server never write them directly.
- Account ids are never reused (profiles and the deleted list are keyed by id). The Postgres sequence must stay at the JSON `nextUserId` when migrating.
- Production has no dev defaults: no seeded `admin/admin`, `SITE_SECRET` (32+ chars), `LOBBY_ADMIN_SECRET` and an https `SITE_ORIGIN` required or the site refuses to start.
- All user text escaped; Markdown sanitised to an allowlist every render; CSRF token on every POST; strict CSP on every page except `/play`.
- Secrets (password hashes, salts, tokens, emails) never appear in logs or reports.
- Guest names are generated client-side (`Guest_<0-9999>`, Game.ts 765) and sent as a guest display name (`pendingAuth` type `guest`); the server must not trust them for rights.
- Rate limiters are bounded (`maxKeys`); keep new limiters on `RateLimiter`.

## How to extend
1. **Add a site page**: handler `router.get('/x', ...)` in `site/src/app.ts` (follow `/pilots`), a view in `site/src/views/pages.ts` returning escaped HTML via `html.ts`, a nav link in `views/layout.ts`; add a test in `site/src/app.test.ts`. POST routes need the CSRF check (use the existing helpers) and a limiter from `security.ts`.
2. **Add an account endpoint**: `UserStore` method in `types.ts`, implement in `JsonUserStore` and `PostgresUserStore`, route in `accounts/routes.ts` (`handleAccount`), limiter, tests in `accounts/accounts.test.ts` / `hardening.test.ts` / `userStore.test.ts`; expose via `LobbyAccounts` if the game server needs it.
3. **Add a site store table**: `site/schema.sql`, `store/types.ts`, both stores, `store/store.test.ts`.
4. **Post an update**: admin panel, or `cd site && npm run post-update -- file.md` (token from admin panel; see the "Posting updates from the terminal" note below).
5. **Move accounts/profiles to or from Postgres**: follow `docs/ops/postgres-migration.md` (re-sync with `scripts/db/vps-sync.sh --verify-only|--dry-run|--replace`; backend chosen by a systemd drop-in `postgres.conf` setting `USER_STORE_BACKEND=postgres`, not in the repo units).
6. **Ship the site**: `WITH_SITE=1 bash deploy/vps/deploy.sh` (see `ops-tools`); without `WITH_SITE` the site is not deployed and the game stays at `/`.

## Tests
- `npx vitest run --pool=forks --no-file-parallelism site server-browser` (from `game-v2/`); `cd site && npm run typecheck`.
- Game-server side: `npx vitest run server/src/auth server/src/profile`.
- Postgres integration (throwaway DB only): see `site/REVIEW.md` "Tests" (`DATABASE_URL` + `SITE_TEST_DATABASE_URL`, apply `server-browser/schema.sql` first). Migration tool: `npx vitest run scripts/db`.
- Dev servers (check the port first, kill by PID): lobby `cd server-browser && npm run dev` (8787), site `cd site && npm run dev` (5310, needs lobby; `/play` needs Vite 5273).

## Gotchas
- Production lobby is 8790, site 8791, game 3100 (nginx in front); dev ports differ (8787, 5310, 3000). `LOBBY_URL` in the site unit points at 8790.
- jsonb does not preserve key order: profiles loaded from Postgres can order object keys differently (only the pilot title tie-break depended on it).
- Production switched to Postgres on 2026-10-31 (~14:33); `docs/ops/postgres-migration.md` now says so and keeps the rollback steps. The JSON files on the VPS are a frozen snapshot of that moment.
- JSON stores can write on load (a `.bak`, an admin flag): migration tools copy the data first and run with `NODE_ENV=production` so no admin/admin seed appears.
- The site's data (`data/site`) is excluded from deploys and kept; a Postgres site store needs `pg` installed in `site/`.
- Deleting an account only removes the profile after a game server heartbeat (10 s); a stale running server will not.
- Dev admin is `admin`/`admin`; guests are admins on dev servers only.

## Notes (moved from DEVELOPMENT.md)
- **Run the site**: `cd game-v2/site; npm install; npm run dev` (http://localhost:5310; needs the lobby on 8787, Play needs Vite on 5273); `npm run typecheck`; tests run with the rest (`npx vitest run --pool=forks --no-file-parallelism`, site/src/*.test.ts). Server-rendered Node + TypeScript, no front-end framework. Features: live pilot count, update feed (Markdown posts, comments, RSS), suggestions board (votes, statuses, admin replies), shoutbox, accounts (sign in, register, pilot card, change password/email, sign out everywhere, delete), public pilot profiles and leaderboards, admin panel, authed API and CLI for posting updates.
- **Accounts are the lobby's**: the site signs in through the lobby (`/auth/login`, `/auth/register`) and keeps the lobby session token in an HttpOnly cookie; account management uses `/auth/account`, `/auth/change-password`, `/auth/change-email`, `/auth/logout-all`, `/auth/delete-account` (`server-browser/src/accounts/routes.ts`). An admin is whoever the lobby says (`isAdmin`). Dev lobby auto-seeds `admin`/`admin` (JSON store, `data/users.json` gitignored; delete to reset).
- **Account storage**: pluggable `UserStore` (`JsonUserStore` default; `PostgresUserStore` selected by `USER_STORE_BACKEND=postgres` + `DATABASE_URL`, schema `server-browser/schema.sql`: `users (id, username, email, password_hash, salt, is_admin, created_at)`, `sessions (token, user_id, expires_at)`). To try Postgres locally: `npm install pg` where needed, `psql $DATABASE_URL -f server-browser/schema.sql`, then run with the two env vars. Production switch and rollback: `docs/ops/postgres-migration.md`.
- **Its own data**: posts, comments, suggestions, votes, shouts, API tokens in `data/site/site.json` in dev, uploads in `data/site/uploads/` (delete the folder to reset). Production: `site/schema.sql` and `SITE_STORE_BACKEND=postgres DATABASE_URL=...` (`npm install pg` in site/). Keep `data/site` out of deploys (like `data/lobby`). Pilot data is read-only from files: `data/profiles/<userId>.json`, `data/profiles/_rankings.json`, `data/status/live.json`, behind `PilotSource` (`src/pilots.ts`).
- **Settings** are environment variables, listed at the top of `site/src/config.ts` and in `site/.env.example` (`SITE_PORT`, `SITE_ORIGIN`, `SITE_SECRET`, `LOBBY_URL`, `LOBBY_ADMIN_SECRET`, `GAME_MODE`, ...). In production (`NODE_ENV=production`) `SITE_SECRET` (32+ chars), `LOBBY_ADMIN_SECRET` and an https `SITE_ORIGIN` are required: the site stops at start naming what is missing.
- **Deleting an account** deletes the pilot's profile too: the lobby keeps the ids deleted in the last 30 days (`data/lobby/deleted-accounts.json`) and answers every game server's 10-second heartbeat (`POST /register`) with them; the server disconnects anyone on the account, deletes `data/profiles/<id>.json` (or the Postgres row) and takes the pilot off the rankings (`GameServer.forgetAccounts`). Ids are never reused (the JSON store keeps `nextUserId`).
- **Production** (`deploy/vps`): `spacegame-site.service` runs the site on 127.0.0.1:8791 as `spacegame`, writing only `data/site/` (never touched by a deploy). `remote-install.sh` makes `SITE_SECRET` once in `/etc/spacegame/secrets.env` and installs the nginx routes as `/etc/nginx/snippets/spacegame-site.conf` (refreshed each deploy), included by the certbot-edited site file in place of its old `location /`: the website is at the root and the game at `/play`. See `site/REVIEW.md`. Store tests run against a scratch database when `SITE_TEST_DATABASE_URL` / `DATABASE_URL` is set (`site/REVIEW.md`, Tests).
- **Play handoff**: `/play` serves the game's own `index.html` from the site's origin with one script first in `<head>` that puts the visitor's lobby session in `localStorage.authToken`, where the client already keeps it (on load it asks the lobby if the token is good and skips sign-in: `Game.ts resumeSession`). No client change, no token in a URL. `GAME_MODE=proxy` (dev default): Vite's page, with `/src`, `/@vite`, `/node_modules`, `/sfx` and the HMR socket passed through to 5273 (http://localhost:5310/play is the live dev game); `static` (production default): `client/dist/index.html` from disk, nginx serves `/assets/` and `/sfx/` from `client/dist`; `link`: redirect to `GAME_URL`. Signing out on either ends the session on both.
- **Posting updates from the terminal**: make a token in the admin panel (Admin, API tokens; only its hash is kept; shown once), then from `game-v2/site`: `export SITE_TOKEN=sgs_...` (or `npm run post-update -- --save-token sgs_...`, stored in `~/.config/spacegame/site-token`), `npm run post-update -- path/to/post.md` (front matter decides draft/published), `--publish`/`--draft`, `--dry-run`, `--list`, `--publish-slug <slug>`, `--unpublish <slug>`, `--delete <slug>`, `--whoami`, `SITE_URL=... ` or `--site <url>` for another site. Without a token it signs in as an admin for that run (`SITE_USER`/`SITE_PASSWORD` or `--login`). A post is Markdown with front matter: `title`, `tags: [..]`, `status: published|draft` (default draft; also `draft: true`/`publish: true`), optional `slug` (file name otherwise, leading `01-` dropped), `summary` (first paragraph otherwise), `cover` (first image otherwise). Local images (and `cover`) upload (PNG, JPEG, GIF, WebP; 8 MB) with links rewritten, same image to the same URL; re-running a file updates its post by slug. Examples: `site/seed/posts/` (images `site/seed/images/`). The same API is plain JSON (`Authorization: Bearer sgs_...`): `GET /api/v1/posts`, `POST /api/v1/posts` (create or update by slug), `PATCH|DELETE /api/v1/posts/:slug`, `POST /api/v1/uploads` (image as body), `POST /api/v1/preview`, `GET /api/v1/me` (see the top of `site/src/app.ts`). Render images for posts with the native renderer (render-ships guide).
- **Security**: all user text is escaped (templates escape by default, `site/src/html.ts`); Markdown is sanitised to an allowlist every time, admin posts too, raw HTML shows as text (`site/src/markdown.ts`); cookies HttpOnly, SameSite=Lax, Secure in production; every form/script POST carries a CSRF token (HMAC of a per-browser cookie) and cross-origin POSTs are refused; rate limits on sign-in, registration, account changes, comments, suggestions, votes, shouts, uploads, bad API tokens (the lobby also limits password checks per address); strict CSP (no inline script) on every page but `/play`; uploads checked by bytes (no SVG) and served with their own `default-src 'none'`; no secrets in the repo, API tokens stored as sha256 hashes.
