# Website, lobby & accounts
Three cooperating services. The **lobby** (`server-browser/`) owns accounts and sessions, keeps the game-server registry, and answers each server's heartbeat. The **website** (`site/`) is a server-rendered Node + TypeScript site (updates feed, suggestions, shoutbox, pilots/leaderboards, account pages, admin panel, an authed posting API, and `/play` which serves the game client signed in). The **game server** talks to the lobby through `server/src/auth/LobbyAccounts.ts` (it never stores accounts itself). The site has no accounts of its own; it signs in through the lobby and keeps the lobby session token in an HttpOnly cookie. Postgres is live in production for accounts, sessions, profiles and rankings (see `docs/ops/postgres-migration.md`; the JSON stores remain the default and dev backend).

## Public interface
- Lobby HTTP: `/auth/*` JSON POSTs (cookie-less; token in body/`Authorization`), `POST /register` heartbeat, `GET /list`; `/admin/*` guarded by `LOBBY_ADMIN_SECRET` (constant-time compared; wrong or empty is 403).
- `UserStore` (accounts/types.ts) is the contract all backends and `LobbyAccounts` implement; add a method to all of them plus the Postgres test.
- `SiteStore` (site/src/store/types.ts) likewise for JSON/Postgres.
- Site posting API: `Authorization: Bearer sgs_...` on `/api/v1/posts|uploads|preview|me`.
- Session sharing: `/play` puts the lobby session into `localStorage.authToken` before the game loads, so site sign-in = game sign-in (Game `resumeSession`).
- Deleted accounts: lobby heartbeat reply -> game server deletes profile and ranking entry. The lobby itself drops the account's inbox and takes it off every friends list (`onAccountDeleted`).
- Ranks: owner > admin > pilot. The lobby's answers carry `isAdmin` (true for the owner too) and `isOwner`; the game's `authResult` carries `isOwner` (only when true), the admin panel's player list `owner`, `AdminAccountInfo.rank` can be `'owner'`.

## Invariants
- Accounts live only in the lobby store; the site and game server never write them directly.
- Account ids are never reused (profiles and the deleted list are keyed by id). The Postgres sequence must stay at the JSON `nextUserId` when migrating.
- Production has no dev defaults: no seeded `admin/admin`, `SITE_SECRET` (32+ chars), `LOBBY_ADMIN_SECRET` and an https `SITE_ORIGIN` required or the site refuses to start.
- All user text escaped; Markdown sanitised to an allowlist every render; CSRF token on every POST; strict CSP on every page except `/play`.
- Secrets (password hashes, salts, tokens, emails) never appear in logs or reports.
- Guest names are generated client-side (`Guest_<0-9999>`, `handleGuestPlay` in Game.ts) and sent as a guest display name (`pendingAuth` type `guest`); the server must not trust them for rights.
- Rate limiters are bounded (`maxKeys`); keep new limiters on `RateLimiter`.
- **Ranks**: an owner passes every admin check (lobby `isAdminRank`, game `conn.isAdmin`, site `isAdmin`). The owner flag (`is_owner`, JSON default false) is set only on the server side: `POST /admin/set-owner { username, isOwner }` with the lobby secret and no `actor`, or `OWNER_USERNAMES` (comma-separated usernames, made owners at every lobby start; taking a name out does not revoke: use set-owner). Owner-only: granting and revoking admin (site Pilots page, game `/rank` and the F2 panel), banning, unbanning or demoting an admin, deleting other people's accounts (site Pilots page, lobby `/admin/delete`), publishing, unpublishing, editing or deleting a published post (panel and API), and API tokens (an existing token publishes only while its maker is the owner). The site has no settings pages (settings are env vars). Admins keep moderation: bans of pilots, comments, suggestions, the shoutbox, hiding shared ships, and drafts. Nobody bans, demotes or deletes the owner through any tool. The site and game send the acting admin as `actor` and the lobby checks the same rules again (`rankRefusal`); calls with the secret and no actor (older game servers) still work, except against an owner.

## How to extend
1. **Add a site page**: handler `router.get('/x', ...)` in `site/src/app.ts` (follow `/pilots`), a view in `site/src/views/pages.ts` returning escaped HTML via `html.ts`, a nav link in `views/layout.ts`; add a test in `site/src/app.test.ts`. POST routes need the CSRF check (use the existing helpers) and a limiter from `security.ts`.
2. **Add an account endpoint**: `UserStore` method in `types.ts`, implement in `JsonUserStore` and `PostgresUserStore`, route in `accounts/routes.ts` (`handleAccount`), limiter, tests in `accounts/accounts.test.ts` / `hardening.test.ts` / `userStore.test.ts`; expose via `LobbyAccounts` if the game server needs it.
3. **Add a site store table**: `site/schema.sql`, `store/types.ts`, both stores, `store/store.test.ts`.
4. **Post an update**: admin panel, or `cd site && npm run post-update -- file.md` (token from admin panel; see the "Posting updates from the terminal" note below).
5. **Move accounts/profiles to or from Postgres**: follow `docs/ops/postgres-migration.md` (re-sync with `scripts/db/vps-sync.sh --verify-only|--dry-run|--replace`; backend chosen by a systemd drop-in `postgres.conf` setting `USER_STORE_BACKEND=postgres`, not in the repo units).
6. **Ship the site**: `WITH_SITE=1 bash deploy/vps/deploy.sh` (see `ops-tools`); without `WITH_SITE` the site is not deployed and the game stays at `/`.

## Gotchas
- Production lobby is 8790, site 8791, game 3100 (nginx in front); dev ports differ (8787, 5310, 3000). `LOBBY_URL` in the site unit points at 8790.
- jsonb does not preserve key order: profiles loaded from Postgres can order object keys differently (only the pilot title tie-break depended on it).
- Production switched to Postgres on 2026-10-31 (~14:33); `docs/ops/postgres-migration.md` now says so and keeps the rollback steps. The JSON files on the VPS are a frozen snapshot of that moment.
- JSON stores can write on load (a `.bak`, an admin flag): migration tools copy the data first and run with `NODE_ENV=production` so no admin/admin seed appears.
- The site's data (`data/site`) is excluded from deploys and kept; a Postgres site store needs `pg` installed in `site/`.
- Deleting an account only removes the profile after a game server heartbeat (10 s); a stale running server will not.
- Dev admin is `admin`/`admin`; guests are admins on dev servers only. The dev lobby's owner is `brotherk3d` (set once with set-owner; the seeded `admin` is only an admin, so it can't grant admin or publish).
- Make someone the owner (server side only): `curl -s -X POST localhost:8787/admin/set-owner -H 'Authorization: Bearer <LOBBY_ADMIN_SECRET>' -H 'Content-Type: application/json' -d '{"username":"name","isOwner":true}'` (dev secret `dev-lobby-admin-secret`; production: on the box, port 8790), or `OWNER_USERNAMES=name` in the lobby's environment.

## Friends
- **Where**: per account in the lobby (Kieran, 2026-11: "Friends should be tied to the account"), so a pilot's friends, requests and status are the same on every game server and the dev and production lobbies each have their own. Game servers read and change them with `/admin/friends/*` behind `LOBBY_ADMIN_SECRET` (game side: `server/src/game/social/LobbyFriends.ts`; see server-core "Friends and private messages").
- **Routes**: `get {userId}` -> `{status, friends, incoming, outgoing}` (entries `{id, name}`, names from `users`, gone accounts left out); `request {userId, name}` -> `result` sent / accepted (they had asked) / already / pending / full / theirFull / busy / self / unknown; `respond {userId, name, accept}` -> accepted / declined / full / gone; `remove {userId, name}` -> unfriended / removed / none; each change answers with both accounts' lists (`me`, `them`). `status {userId, status}` (online, away, busy, invisible). `import {accounts}`: a game server's old per-server document, merged once (idempotent). Unknown or deleted `userId`: 404.
- **Checked here**: ids, names (40 characters), the status, the caps (100 friends, 50 waiting), and limits per account: 10 requests / 10 min, 6 status changes / 30 s, 60 other changes and 120 reads a minute (429 with `limited: true`); 20 imports an hour.
- **Presence is not kept here yet**: each game server counts only its own pilots as online. The seam: servers report their online account ids (the `/register` heartbeat is the cheap place) and get their pilots' friends' presence back; cross-server private messages would route the same way.

## Activity feed
- **Flow**: each game server queues events (`server/src/activity`) and POSTs batches to its lobby's `/admin/activity/ingest` with `LOBBY_ADMIN_SECRET` (wrong or no secret: 403; the name "Lobby" is refused; at most 200 events a call, 120 calls a minute per server name). Lobby down: the server keeps the newest 2,000, backs off up to a minute, and says how many it lost. The lobby stores them per server name (JSON in dev, the Postgres `activity` table in production) and adds its own sign-ins as "Lobby".
- **Reading**: the website asks each lobby in `ACTIVITY_LOBBIES` server to server (`POST <lobby>/activity/read { token, filters }`). The site's own lobby takes the visitor's session; another (the production lobby read from the dev site, `https://space.brotherk3d.com/lobby`) takes a session made by signing in to it on the Activity page, kept in an HttpOnly cookie `sg_act_<source>`. Only admins (and the owner) of that lobby get events. A lobby that doesn't answer like the feed shows "<name> feed not available yet".
- **Event types** (`ACTIVITY_TYPES` registry in `server/src/activity/index.ts`): on by default are joins and leaves (with session length), public chat lines (text cleaned, 200 characters at most, 20 a minute per pilot like every type), admin actions, kicks, refused sign-ins, protocol mismatches, server errors, server start/stop and the dropped notes; the lobby always adds sign-in, sign-out, new accounts and account changes. Off by default, emitters kept: deaths and PvP, PvE kill/mining/salvage summaries, crafting, sales, trades, docking, level-ups, quests, ship swaps/builds/refits, boss fights, private-message and friend counts. Switch them with `ACTIVITY_TYPES` in the game server's environment: `+death,+boss_kill` adds, `-chat` removes, `all`, or a plain list replaces the defaults.
- **Never** private-message or party-chat contents, mail or announcement texts, passwords, emails or tokens.
- **Production**: nothing flows until the new game build (game server + lobby) is deployed: the lobby makes its table at start, and nginx needs the new `/lobby/activity/` location (in `deploy/vps/nginx-spacegame-game.conf`, installed by the deploy). The production game server already has `BROWSER_URL`, `LOBBY_ADMIN_SECRET` and `SERVER_NAME=AUS Main`.
- **Dev check**: run the lobby, game server and site as usual, sign in to http://localhost:5310 as `admin`/`admin`, Admin, Activity.

## Notes (moved from DEVELOPMENT.md)
- **Run the site**: `cd game-v2/site; npm install; npm run dev` (http://localhost:5310; needs the lobby on 8787, Play needs Vite on 5273); `npm run typecheck`; tests run with the rest (`npx vitest run --pool=forks --no-file-parallelism`, site/src/*.test.ts). Server-rendered Node + TypeScript, no front-end framework. Features: live pilot count, update feed (Markdown posts, comments, RSS), suggestions board (votes, statuses, admin replies), shoutbox, accounts (sign in, register, pilot card, change password/email, sign out everywhere, delete), public pilot profiles and leaderboards, admin panel, authed API and CLI for posting updates.

- **Deleting an account** deletes the pilot's profile too: the lobby keeps the ids deleted in the last 30 days (`data/lobby/deleted-accounts.json`) and answers every game server's 10-second heartbeat (`POST /register`) with them; the server disconnects anyone on the account, deletes `data/profiles/<id>.json` (or the Postgres row) and takes the pilot off the rankings (`GameServer.forgetAccounts`). Ids are never reused (the JSON store keeps `nextUserId`).
