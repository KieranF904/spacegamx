# Bit-pack audit: what still went plain after the netcode rounds (2026-11-06)

Kieran: "bit pack anything that is pending to be bit packed since the NetCode update". Every joined client gets its
frames through its `PackedLink` (common network/packed): a snapshot as encode-once blocks (`PK.BLOCKS`), a handful of
hot messages field by field (`PACKED_FIELDS`), hits and part HP their own way, and everything else as
`PK.LEGACY`: the base binary codec's bytes inside the bit stream (a compact row if the type is in `COMPACT`, else the
whole object with its key names). Several messages added in protocols 56-60 (gunCtl, gunSync, pulls, ownSync) were
plain, and `gunCtl` was the biggest single message in a fight after the snapshot.

## How it was measured

`PackedEncoder.bitsByType` (new) counts the bits each message type took in the real packed frames (`type(plain)` for a
message that went as base bytes; `(frame)` the frame byte, resets, sub-frame ends and padding), and `blockBits` the
BLOCKS snapshot's parts (now split: `n`, `d`, `x`, `w`, `hh`, `g`). The crowd bench prints both per client per second:
`cd server && npm run bench:crowd -- --layouts ball,spread,cruise,boss --n 20,50` (10 s each, 4 probes, latency 3
ticks), result fields `packedBps` (every client) and `packedProbeBps` (the probes). The figures below are the **probes**:
they answer as a game client does (hit reports, own and body checks). The bulk sockets owe nothing back, so they get
`hitFix` corrections a real client wouldn't (`hitFix(plain)` 353 B/s at ball 20 for them, about 1 B/s for a probe).
The bench has no separate mining scene; boss 20 is the Scrap Mother fight with 20 pilots. Runs are seeded but not
bit-identical run to run (a few % either way on fight-driven rows).

"Before" is the branch at 180fad1 with only the counters added; "after" is this change.

## What was done

1. **Gun rows into the snapshot** (the biggest): `ServerSnapshotMessage.gun` (compact field `g`, index 15; the packed
   snapshot's field mask is 15 bits). GunNet already made each pilot's row once a round for every client; it is now an
   encode-once block (`BlockStore.gunRow`: the pilot's wire id, then rowsIO `gunRowBody`: a run bit, the events less
   one, each event's trigger bits, ticks ago in 3 bits (7: a varint more) and the distance step, `PK_GUN` chunks
   [2, 3, 3]). The chunks are fitted to a dump of ball 50's 4,464 rows: 70 % one event, 47 % of steps ±1, 75 % within
   ±3; the bits land at 25.7 a row against 28.1 for the first guess. Through PK.SNAPSHOT (no blocks) the same body
   follows the pilot's slot (`gunRowsIO`). The client takes the rows first thing in its snapshot handler
   (`OtherGuns.onGunCtl({t, r})`; the `ServerGunCtlMessage` type is gone, `GunCtlRows` is what the lanes take). A
   snapshot carrying gun rows is urgent (`urgentFor`: 'gunRows'), as the gunCtl message made its frame before, so
   every frame goes when it did (the golden frame counts are unchanged).
2. **Other pilots' rough cursor distance** (the status row's `data[5]`, in hundreds: the drawing fallback for a
   client not stepping that pilot's lane). Before, it was the cursor's own, so a pilot sweeping its cursor re-sent its
   status row to every holder each time it crossed a hundred. Now it moves by GunNet's idle rule, firing or not
   (`GunLane.rough`, SnapshotBuilder `roughCursor`): idle, it is what the lanes were sent; with a trigger held, the
   cursor's whenever the change would turn a gun's line by IDLE_TURN at IDLE_MIN_GAP (not every held-distance step).
   An unarmed pilot (no lane, no turrets to draw) keeps the cursor's. Measured with a bench-only switch (removed):

   | status rows (snapshot.e), probes, B/s | ball 20 | ball 50 | spread 20 | spread 50 | boss 20 |
   |---|---:|---:|---:|---:|---:|
   | the cursor's (before) | 1073 | 2788 | 162 | 161 | 173 |
   | the lane's distance as sent (exact while firing) | 704 | 1896 | 116 | 128 | 172 |
   | **the idle rule, firing or not (now)** | **588** | **1706** | **104** | **107** | **157** |
   | none at all (the floor: the field always 0) | 385 | 830 | 72 | 43 | 82 |

   So the cursor distance was 40-70 % of the status rows in a fight (ball 20: 688 of 1073 B/s); the idle rule takes
   70 % of that at ball 20, 55 % at ball 50. What's left (203 and 876 B/s) is pilots swinging their aim while firing.
   Sending it only to clients that don't step the lane would take most of the rest, but a row object is one block for
   every holder (encode once), so it would need a second row per pilot and per-client keys; left for now.
3. **Field-by-field packing for the rest that showed up** (`PACKED_FIELDS`, message codes now 5 bits: `PK_BITS` 5, codes
   16-22): `gunSync` (the tick and `w` as steps under one key, `z` as a list), `mapDots` (a new field kind `r`: a flat
   list in rows of n, each value the step from the same column of the row before: dots, routes, info, pts), `debrisSplit`,
   `bossBeam`, `bossTelegraph`, `bossBlow`, `pulls`. `gunSync` and `pulls` joined `COMPACT` (appended) to be packed.
   The extra bit per message code costs about 3 B/s a client (the `(frame)` row).

## Left plain, and why

- `profile` (115-320 B/s in a fight): the economy family's whole profile, sent again on any change (an XP gain, a credit,
  ammo): a delta message would do far more than packing it. Economy, not netcode; worth its own change.
- `items`, `gained`, `toast`, `effect`, `hangar`, `systemMessage`, `bossPhase`, `friends`: under 70 B/s each, one-off or
  UI messages with strings.
- `cells` (3-17 B/s), `crowd`, `pops`, `hitFix` (about 1 B/s for a real client), `netCaps`, `ownSync` (4-17 B/s; most
  are the hazards-only form): small; compact already where they are in `COMPACT`.
- `gunSync`'s `z` steps poorly as a list (its numbers are unlike each other): 66 -> 59 B/s at ball 20. A kind of its own
  for `packGunSync`'s layout would do better; it's 1-2 % of a fight.
- Control rows (`snapshot.c`, a third of a fight's bytes) and status rows were bit-packed already; nothing here
  changes them beyond the cursor rule.

## Gun rows kept urgent

`gunCtl` was never in PackedLink's `CAN_WAIT`, so in a fight nearly every snapshot frame went at once (no coalescing).
That is kept here (behaviour unchanged). Letting them wait like the rest of the snapshot (measured with a bench-only
switch, removed; probes):

| | ball 20 | ball 50 | boss 20 |
|---|---:|---:|---:|
| messages a second, urgent (now) -> waiting | 14.8 -> 10.6 | 20.5 -> 13.0 | 16.6 -> 10.4 |
| wire B/s (66 B a message) | 3915 -> 3646 | 13026 -> 12356 | 4729 -> 4311 |

About 270-670 B/s on the wire and a third of the messages, with the tick layer still exact (no disagreements, no told
ticks, no fixes). Other pilots' trigger changes would then reach a client up to COALESCE_TICKS (3) later, as fire
records did before protocol 59. Kieran's call: one line in PackedLink `urgentFor`.
