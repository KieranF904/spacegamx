# Profile: where the time goes (31 October 2026)

Measured, not guessed. Client frame time in busy scenes, server tick time in a boss fight, and cold load. This follows
up `rendering.md` (items 1, 2, 3, 4, 6, 7, 8, 9, 10, 13, 14, 21 and 22 are marked fixed) and `collisions.md`.
Nothing in the game was changed. Raw profiles, traces and per-scene JSON are in the session scratchpad, not the repo.

**Headline.** Steady-state frames are cheap on this machine: the busiest fight costs **4.2 ms of main-thread time per
frame** and under ~2 ms of GPU time. The things a player actually feels are **one-off stalls**:

- a **5.2 s main-thread freeze from shader compilation** on a first visit (4.0 s of it is the sun shader, compiled twice);
- **95 to 165 ms hitches** from shaders compiled lazily on first use, right after joining.

Within the steady-state frame, **Pixi's own scene-graph work is 42%**. It is driven by thousands of pooled effect sprites
and by the bloom re-rendering its sources. The server is far from its budget (1 to 2 ms a tick of 16.7).

## 1. Method

**Machine.** AMD Ryzen 7 9800X3D, RTX 5070 Ti, Windows 11. Chrome headless (the render daemon's one Chrome, ANGLE/D3D11,
**idle process priority**), 1440×900 CSS px at DPR 1 unless stated. The headless GPU path is not Kieran's normal
windowed browser (no real display or compositor vsync, idle priority, a fresh profile), and this CPU is near the top for
single-thread speed. **Read the absolute numbers as a best case and the ratios as the point.** A typical player laptop
will be roughly 2.5 to 4× slower on the JavaScript, which puts the busiest fight at about 10 to 17 ms a frame: at or past
the 60 Hz budget.

**Client.** `scripts/profile/clientProfile.mjs` (new, measurement only) borrows a tab from the render daemon, joins the
dev game (Vite 5273, dev server 3000) as a guest, and builds each scene with admin chat commands (`/god`, `/tp`, `/boss`,
`/spawn`). For each scene it records:

- a DevTools CPU profile (`Profiler.start`/`stop`, 250 µs sampling, 8 to 10 s);
- in-page timings of the frame's parts, taken by wrapping instance methods from the page (`Game.update`,
  `Renderer.update` and its steps, `ShipRenderer.update`, `WeaponFx`, lighting, bloom, HUD `update()`s, the network
  handler, and Pixi's `renderer.render` split into the main pass and render-texture passes);
- WebGL draw calls per frame, frame intervals, and long tasks.

Other measurements:

- **GPU:** a probe that reads one pixel after the main pass, which waits until the GPU has finished the frame. It was run
  with layers switched off one at a time (via `renderable`, which the game never touches), at each quality tier and at
  three resolutions.
- **DOM work:** a 5 s timeline trace of the fight (style, layout, paint, and the GPU process).
- **Load:** a full trace from navigation to flying (main thread and workers), with every shader program's link timed
  from document start.

The script survives Vite full reloads, which happened twice while other agents were editing. It re-joins and rebuilds
the scene.

**Server.** `server/src/bench/profileBench.ts` (new, measurement only). It runs a full `GameServer` with 8 pilots: 5 at
the Redtooth picket boss's lair and 3 by the sun. There are 14 hostile packs around them and 20 more packs across Sol
that nobody is near. The pilots are healed every half second and are always firing at the nearest hostile. The bench
wraps every system in `GameServer.tick` (plus the AI controllers, contacts, NPC guns, `hurt`, `splashAt` and
`segmentHit`) with timers, and takes a `node:inspector` CPU profile of the tick loop only. The timers cost about 7% of
the tick (the `obj.<computed>`/`now` rows). I also ran the stock `tickBench` (default and `--scenario spread`), the
`collisionBench`, and a heavy run (20 pilots, 40 packs). No test suites were run while profiling.

**Scenes (client).**

| scene | what's in it |
|---|---|
| idle | Guest at the Sol spawn, nothing hostile; ~560 asteroids in state; 33 draws/frame |
| map | System map open (the world isn't drawn) |
| hangar | Hangar open (the world is paused) |

| boss-arrive | The teleport into the fight, the boss and the packs coming into view |

Every scene held 57 to 60 fps (the headless frame clock). There were no long tasks in steady state.

- **The Low tier doesn't lower CPU at all.** It made the sun scene slightly heavier: more ships came into view and the
  draw calls rose. The tiers only change GPU-side knobs (MSAA, DPR, star layers, bloom size). A CPU-bound laptop gets

  runs every frame.

## 3. Client: GPU (relative)

Probe: the main pass followed by a 1-pixel `readPixels`, mean over about 4 s. The "bare" row (no world, no sky, no
bloom: 5 draws) is the probe's own sync cost of **~1.4 ms**. Subtract it to get the frame's GPU work. Hostile counts
drifted as packs died, so expect ±0.3 ms noise.

| 3840×2160 (1920×1080 CSS at DPR 2, High) | probe ms | minus the floor | layer's share |
|---|---|---|---|
| everything | 3.57 | **2.1** | |
| no sky (star layers + haze) | 2.28 | 0.8 | **sky ≈ 1.3 ms (the largest)** |
| no sun / glow / corona | 2.95 | 1.5 | sun quads ≈ 0.6 |
| no ships | 3.03 | 1.6 | ships ≈ 0.5 |
| no effects | 3.13 | 1.7 | effects ≈ 0.4 |
| no bloom | 3.33 | 1.9 | bloom ≈ 0.25 |
| no world (sky + bloom only) | 2.29 | 0.8 | |
| Medium (DPR 1.5) | 2.48 | 1.0 | −50% |
| Low (DPR 1; MSAA still on, since it is fixed at start) | 2.41 | 1.0 | −50% |
| 2560×1440 at DPR 1, High | 2.58 | 1.2 | |
| 1440×900 at DPR 2, High | 2.73 | 1.3 | |
| 1440×900 at DPR 1, High | 1.72 | **0.3** | |

- **On this GPU the GPU is nowhere near the limit:** about 0.3 ms at 900p and about 2 ms at 4K.
- The cost scales with pixels. The **sky's star layers are the biggest single GPU item at high resolution** (rendering
  #16), then the sun's quads (#15).
- Medium and Low halve it, almost all through DPR.
- I couldn't isolate MSAA on this card: start-up Low (no MSAA) and runtime Low (MSAA on) were within the noise.
- GPU timer queries (`EXT_disjoint_timer_query_webgl2`) were tried and rejected. On ANGLE/D3D11 they count the CPU's
  gaps between submissions ("bare" read 0.02 ms, "no world" 2.7 ms).
- A SwiftShader (software GPU) sweep, as a stand-in for a weak GPU, ran at about 1 fps, too few frames to rank reliably.
  It roughly agreed: world about 45%, sun/glow/corona about 30%, sky about 20% of fragment work.

**Bundle.** The production build is **broken right now**: `vite build` fails because `client/src/ships/ProtoTools.ts`
pulls in `server/src/game/SystemMemory.ts`, which imports `fs`. So these numbers are from the existing `client/dist`

## 6. The ten most valuable optimisations (ranked)

Gains are on this machine. Multiply the ms by about 3 for a typical laptop.

| # | What | Measured cost now | Expected gain | Effort | Audit item |

## 7. Surprises

1. **The worst thing a player meets is a 5-second freeze on the first visit, from shader compiles.** The sun shader
   alone is 4 s, because it compiles twice: once for the login screen's own Pixi app and once for the game. It never
   shows up when developing, because Chrome caches the binaries.
2. **Steady-state frames are cheap** (4.2 ms in a 112-ship fight with a boss) and **42% of that is Pixi's own
   bookkeeping**, not game logic. The levers are object count and redundant render passes, not algorithms.
3. **The bloom's extra passes cost as much CPU as drawing the whole scene once.** Item #14's "render the sources once"
   isn't in the code yet.
4. **5,500 display objects, 3,400 of them hidden.** Pooled sprites only ever accumulate.
5. **The quality tiers do nothing for CPU-bound machines.** They are all GPU knobs, and Auto steps down on frame time,
   so a slow-CPU laptop drops to Low and gains nothing.
6. **The GPU is idle on this card** (≤ 2 ms even at 4K). The sky's star field, not the sun or the bloom, is the biggest
   GPU layer at high resolution.
7. **DOM HUD style, layout and paint is only ~0.3 ms/frame.** The DOM-overlay design is fine.
8. **The server has about 10× headroom** (1 ms mean with 8 pilots in a boss fight). Snapshot building per pilot is the
   part that grows.
9. **The production build doesn't build** (an `fs` import reaching the client through ProtoTools).

## 8. Re-running

```bash
# client (needs Vite on 5273 and a dev game server on 3000; borrows the render daemon's one Chrome)
node scripts/profile/clientProfile.mjs <outDir> load,idle,map,hangar,boss,sun,gpu,msaa
#   any subset; writes <scene>.cpuprofile, <scene>.json, load.trace.json, boss.trace.json, boss-census.json
#   SOFTGL=1 (a SwiftShader daemon) for the software-GPU sweep; GPU_METHOD=timer for timer queries (unreliable on ANGLE/D3D11)
# server (in server/)
npx tsx src/bench/profileBench.ts --seconds 40 [--pilots 8] [--packs 14] [--prof out.cpuprofile]
```

The client script hooks only the page (it wraps instance methods and WebGL calls from DevTools). It spawns hostiles at
the Redtooth picket lair and by the Sol sun, and `/clear`s them afterwards. Stop the render daemon when you're done
(`POST 127.0.0.1:5281/shutdown`, or it quits after 2 idle minutes).
