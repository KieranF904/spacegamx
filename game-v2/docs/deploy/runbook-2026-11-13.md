## (c) The deploy

```
WITH_SITE=1 bash deploy/vps/deploy.sh
```

`WITH_SITE=1` because the last deploy used it (`with_site=1` in the live `REVISION`) and the website's new pages ship
this time. Without it the running website is left on the old code.

What it does, in order: validates the data; builds the client locally; tars; copies the box's current tarball to
`/root/spacegame.prev.tgz`; uploads; pipes the Pushover and PayPal lines into the secrets file; on the box builds
common, server, lobby and type-checks the site in `/opt/spacegame/.build` (services still running); installs the nginx
snippets and runs `nginx -t` (on failure puts them back and stops, nothing else changed); stops the three services; swaps
the code; syncs `data/`; installs the units; restarts; records the release. Expect `Deployed.` at the end. Downtime is
the swap and restart, a few seconds.

If it stops after "systemctl stop" and before "Deployed.", the game is down: fix and run it again, or roll back (f).

## (d) Profile upgrade to v6

**When: straight after `Deployed.`, with the game server stopped for about a minute.**

Why there and not earlier or later:
- The tool must run the new code against the new game data (`/opt/spacegame/data` after the sync): the repair bank's
  size and the kit recipes come from it. Before the deploy the box has the old data.
- The new server is safe with v5 saves: `login` runs `migrateProfile` and saves the result at once, so there is no half
  state while it runs. The stop is only so a pilot who logs in during the upgrade is not saved over (the tool also
  refuses to apply while a lease is held, and only writes rows still below v6).
- Running it before anyone has played on v6 keeps the backup table a clean rollback point.

Steps:
```
# 1. stop the game server (the lobby and website stay up)
SSH 'systemctl stop spacegame-server'

# 2. dry run on the box: read-only transaction, prints one block per pilot. Must end "0 FAILED".
bash scripts/deploy/vps-upgrade-profiles-v6.sh --dry-run

# 3. apply: one transaction. Copies profiles to profiles_pre_v6, writes the rows, or writes nothing if any check fails.
bash scripts/deploy/vps-upgrade-profiles-v6.sh --apply

# 4. check, then start
SSH 'set -a; . /etc/spacegame/secrets.env; set +a; psql "$DATABASE_URL" -X -At -c "SELECT version, count(*) FROM profiles GROUP BY 1" -c "SELECT count(*) FROM profiles_pre_v6"'
SSH 'systemctl start spacegame-server && sleep 3 && systemctl is-active spacegame-server'
```
Expected: `6|8` and `8`. Reports are kept on the box in `/root/profile-upgrade-v6/`.

The dry run on a copy of production (2026-11-12, all 8 at v5) passed every check: see the table in the hand-over report.
What changes per pilot: retired kits and bonds leave storage and their recipe inputs go into the repair bank's
deposits; the kit slots on the quick bar clear; the bank is made (free part full); one login notice; `tutorial` is
filled in as "left". One pilot (#6) was flying a loaner: the loaner record is replaced by a fresh starter in the same
slot. Two pilots (#4, #8) have guns turned by the gun shape rules (`rot` only, which any load does). XP, level, credits,
skill points and ship counts are unchanged for all eight.

Not written by the tool, still happens at each pilot's next login: the retired-skill refund (pilot #2: skill points 6
to 7) and the training-yard offer for returners.

Nothing else needs a migration: `position.at` (landmark tracking) is optional and absent in every production save;
newsletter consent and donations are lobby tables keyed by account, not profile fields.

## (f) Rollback

**Code, data files, units, nginx** (one command; about ten seconds of downtime):
```
bash deploy/vps/deploy.sh rollback 20261107-011439
```
It uploads this machine's `remote-install.sh`, puts back that release's nginx snippets (tested with `nginx -t` first),
stops the three services, hard-links that release's `common server server-browser client site` back into place, syncs
its `data/` files (runtime folders untouched), installs its unit files and restarts. `current-release` then points at
`20261107-011439`. The tarball of that build is also at `/root/spacegame.prev.tgz` after this deploy.

**Profiles** (only if step d was applied). The old build is PROFILE_VERSION 5: it loads a v6 save but drops what it
does not know (the bank, `tutorial`) and the kits are already gone. Put the saves back before starting the old server:
```
SSH 'systemctl stop spacegame-server'
SSH 'set -a; . /etc/spacegame/secrets.env; set +a; psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -c "BEGIN; UPDATE profiles p SET version = b.version, data = b.data, updated_at = b.updated_at FROM profiles_pre_v6 b WHERE p.user_id = b.user_id; COMMIT;" -c "SELECT version, count(*) FROM profiles GROUP BY 1"'
SSH 'systemctl start spacegame-server'
```
This throws away whatever those pilots did on v6. Accounts made after the deploy keep their v6 saves (the old build
reads them as fresh-ish v5 saves; nothing is lost that the old build has).

**New tables and marks**: leave them. `donations`, `newsletter_consent`, `admin_messages`, `ranking_rows`,
`profile_leases` are unknown to the old build and harmless. `game_docs.rankings` keeps its data with an extra
`movedToLobby` field the old build ignores; ranked stats earned on the new build live only in `ranking_rows`.
**Do not drop `donations`**: it is the record of real payments.

**Secrets**: the `PAYPAL_*` lines stay in the file; the old lobby does not read them. Donations stop being offered
because `/support.html` and `/lobby/donations/` go with the old nginx snippet.

**Clients**: a tab on protocol 74 meets the old server (62), gets code 4002 and the reload prompt; the reload serves the
old bundle.

**Whole database, last resort** (a broken table, not a bad release): restore `pre-deploy-20261113.sql.gz` into a new
database and compare or swap, following `docs/ops/postgres-migration.md`. The dump is plain SQL without `--clean`, so it
does not load over the live tables. It would also remove donations made since. Do not do this without the owner.

**Runtime files**: `/root/spacegame-pre-deploy-20261113.tgz` has `data/site`, `world`, `contributor`, `lobby`,
`profiles`, `status` as they were (step b8), should the old site or server not read what the new one wrote.

## (g) Open risks, ranked

1. **The in-game Rankings tab has no route in production (fix before deploying).** The client reads the boards from
   `https://space.brotherk3d.com/lobby/rankings/view`; `nginx-spacegame-game.conf` has no location for it, so the
   request falls through to the website and gets a 404, and the tab shows rankings as down. Add after the
   `/lobby/donations/` block (not edited here: another agent has the nginx confs open):
   ```diff
   --- a/game-v2/deploy/vps/nginx-spacegame-game.conf
   +++ b/game-v2/deploy/vps/nginx-spacegame-game.conf
   @@ location /lobby/donations/ {
        proxy_set_header X-Forwarded-For $remote_addr;
    }
    
   +# The rankings (the Jobs window's Rankings tab reads the boards from the lobby, which ranks every server's pilots
   +# together). Open to any caller; the lobby limits per address (set here, not passed on). /admin/rankings/ stays off
   +# the public side.
   +location = /lobby/rankings/view {
   +    proxy_pass http://127.0.0.1:8790/rankings/view;
   +    proxy_set_header Host $host;
   +    proxy_set_header X-Forwarded-For $remote_addr;
   +}
   +
    # The donation page (client/support.html): a static page of the game's build, served here whether or not the website
   ```
2. **Live PayPal from the first second.** `PAYPAL_ENV=live` keys go to the box in the deploy; there is no dry step
   between "deployed" and "taking money". If the $1 tests fail, turn donations off by removing the three `PAYPAL_*`
   lines from the secrets file and restarting `spacegame-browser` (the page then says donations are unavailable).
3. **The tree is still moving and uncommitted.** The pre-flight below is a snapshot of 2026-11-12 about 13:20. Rerun
   it (b4) on the frozen tree; commit (b5) so the release can be rebuilt.
4. **No off-box backup (SD-13, deferred).** Every backup is on the same disk as the database. Step b9 is the only copy
   elsewhere.
5. **Site catalog is stale** (b3). Not fatal: the site would describe yesterday's parts.
6. **No owner account in production.** `/admin/donations`, publishing posts, tokens and rank changes are owner-only and
   nobody is owner (b6).
7. **Rollback after the profile upgrade loses v6 progress** for anyone who has played since (f). Decide quickly: the
   first ten minutes are cheap, a day later is not.
8. **CSP is still report-only** on the game page, by design. Enforce after a clean console on live (rename the header
   in `nginx-spacegame-play.conf` and `nginx-spacegame-site.conf`, deploy).
9. **`/play` gets two sets of security headers** once nginx adds its own to the website's (`X-Frame-Options: DENY` from
